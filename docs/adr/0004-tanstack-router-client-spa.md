# Client-side routing with TanStack Router

Replace the hand-rolled History API + `useState` routing with TanStack Router, kept as a purely client-side SPA router. The Cloudflare Worker is unchanged: it stays a JSON API that falls through to `env.ASSETS.fetch` with single-page-application fallback, and does not render or server-route any HTML. The router runs entirely in the browser.

Routes are defined as a code-based tree (no file-based routing plugin, no generated route tree) because the app has only a handful of top-level routes. The URL scheme is redesigned from query-param sub-views to nested paths: `/children/$childId/day`, `/children/$childId/prizes`, `/children/$childId/review`. The selected activity date stays a typed, validated search param (`?date=YYYY-MM-DD`) on the day and review routes, because it is a selection within a view rather than a separate page. Old query-param URLs (`/children?day=…`) are not redirected; there are no external bookmarks to preserve.

Alternatives considered: React Router (library mode) — more ubiquitous, but weaker type-safety for search params, which is the exact pain here; a full-stack framework with SSR on the Worker (React Router framework mode / Remix, or TanStack Start) — rejected because this is a small app behind Cloudflare Access and SSR adds Worker complexity for no real benefit; keeping the hand-rolled router — rejected because the query-param dispatch read `window.location` directly from inside feature components.

Auth gating and the in-flight-save lock are **view-overrides at the root route, not router redirects or navigation blockers.** When not signed-in, the root renders the sign-in UI over whatever route is active; when a child or rule save is locked (saving / uncertain / conflict), the root renders that feature's recovery UI over the active route. In both cases the URL is left untouched and navigation stays unblocked. This is deliberate: the save-recovery design (see the module store in `src/features/children/requests.ts`) preserves an uncertain action across unmount, resume, and reload so the parent can navigate away and recover later. A `beforeLoad` redirect guard or a `useBlocker` would fight that design and break the tested "browser Back preserves an unconfirmed action" behavior, so route-native variants of both were rejected in favor of the override mechanism the app already relied on.

# Accept scheduled rule saves at the final database date guard

In the live parent discussion for [issue #6](https://github.com/nurcahyopujo/daily-stars/issues/6), we chose the final database date-guard evaluation, conditional on a successful transaction commit, as the acceptance boundary for scheduled rule saves. Their effective date is the following Jakarta calendar day, explicitly shown in the success message; this deliberately replaces the baseline physical commit-time requirement because the [D1 research](../research/d1-mutations.md) found no documented conditional commit clock, and the parent preferred acceptance time over request receipt time.

A guard passing before midnight may commit afterward without changing the effective date. A confirmed date-guard rollback permits one automatic midnight retry per request with unchanged revision and the same intent; a matching success receipt always preserves the original result, a changed revision requires review, and an uncertain outcome retains its action ID for recovery. SQL clock freshness, advancement across statements, and alignment with Jakarta boundaries remain local/staging verification gates: this decision does not claim the guard has been implemented or proven, and failed clock evidence must reopen it. See [the specification](../../mvp-spec.md#4-data-model-and-invariants) for the approved retry contract and acceptance cases.

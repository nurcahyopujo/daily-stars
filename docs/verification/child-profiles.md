# Child-profile implementation

Implemented the agreed child-profile slice of [F2](../../mvp-spec.md#f2-child-profiles), rather than the entire profiles-and-rules milestone. Settings supports create with ordered optional initial templates, rename, active and archived lists, and archive from tomorrow. Existing React/native controls, CSS tokens, session handling, prepared SQL and the numbered migration directory were reused; there is no component library or new dependency.

The top-bar hamburger menu offers **Home**, **Manage children**, and **Profile**. Launch remains Home, which displays the welcome hero and supporting introduction. Profile contains the existing sign-in/session screen and Sign out action. Authentication loading, sign-in challenges and access failures still show the access screen when needed. The menu closes after selection, outside clicks or Escape, and Escape restores focus to the hamburger button. Child management opens independently of the Profile screen. Add and edit use a native modal dialog with a scrollable phone layout, background interaction/scroll blocking, initial nickname focus and focus restoration to the opening button. Cancel or Escape closes an unsaved form. Saving, unconfirmed and stale-edit states keep the dialog open with recovery controls inside; Escape cannot discard a surviving action. Restoring the page reopens the dialog for any surviving save action.

Navigation uses native links and the browser History API: `/` is Home, `/children` is Manage children, and `/profile` is Profile. `/home` also opens Home, and trailing slashes are accepted. Direct navigation and refresh use the existing Worker SPA asset fallback; browser Back/Forward synchronizes the displayed screen. Unknown paths show Page not found. Sign-in links retain the requested path. If Back changes the URL during an unconfirmed save, its modal stays mounted until reconciliation so the original action ID and intent survive. No routing dependency was added.

The child list uses **Active** and **Archived** tabs with counts and separate empty states. Active opens by default; children with an archive date still in the future remain active. Arrow keys, Home and End select and focus tabs. Adding a child from either tab returns to Active after confirmed success; add/edit modals and save recovery are shared by both lists.

## Behavior and boundaries

- Nicknames are trimmed and validated as 1–60 Unicode code points. Duplicate nicknames are allowed; stable child IDs distinguish profiles. Renaming updates the shared child record without changing assignment dates or identity.
- Creation saves the child, revision-one assignments effective today, audit record and success receipt in one batch. Empty assignments are valid. Selected templates must exist and have an active version today; the transaction rechecks this eligibility. Assignment array order is retained.
- Archive takes effect on the next Jakarta date. Default API lists omit children from that date; Settings retains them under Archived children. Repeating archive with another intentional action preserves the original archive date. No restore/cancel-archive operation was added. No existing assignment or historical row is deleted.
- Profile revisions record the verified parent ID/email and UTC timestamp. Receipts are scoped to parent ID and action ID, fingerprint normalized submitted input, and retain the original full success result/status without expiry. Reusing a key with different input is a conflict. Writes and receipts commit together; zero-row updates are asserted inside the batch.
- Creation and archive use the final SQL date guard. Confirmed date-guard rollback permits one retry with recalculated dates and unchanged intent/key. Matching receipts take precedence over stale-edit classification and preserve their original dates, including after midnight. The implementation uses D1's documented [batch rollback primitive](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch); staging clock behavior remains a separate gate below.
- One frontend request/save module owns timeouts, memory-only action IDs, submitted intent, retry, conflict review and success. Unconfirmed saves retain their key across screen unmount/page restoration and session rechecking. Another edit waits for reconciliation. A stale edit compares current and attempted changes; Apply my change creates a new action against the reviewed revision. Every acknowledged save refetches current server data, including receipt replays. Sign-out or changing parent clears the saved client state; reloading discards it.
- Local Vite middleware admits only loopback requests with a local Host and an explicit mock flag. It supplies a synthetic parent for session/profile routes, uses the shared mutation boundary and profile operations, and runs SQL through Wrangler's local platform proxy with remote bindings disabled. Built preview and the deployed Worker retain Access JWT verification.

The glossary already defines Child, Parent, Template and Assignment accurately; this slice introduces no new domain term or architectural decision requiring an ADR.

## Local evidence — November 9, 2026

`npm run check` passed: TypeScript, 23 Worker/D1 tests, production build, and 44 browser tests (22 per phone-sized Chromium/WebKit project). Tests apply checked-in migrations `0001` and `0002` through Cloudflare's Vitest integration using workerd and the configured compatibility date `2026-11-08`. The Worker configuration has no Node compatibility flags; browser production-build tests exercise the built Worker separately from the test harness. Wrangler version: `4.158.0`.

Storage tests use direct primary binding reads and `DB.batch(preparedStatements)` against real local D1. They verify persisted child/assignment/audit/receipt rows, and empty assertion rows after completion. Cases include same-day ordered setup, empty assignments, invalid/retired/future templates rolling back earlier setup writes, simultaneous identical actions, lost-response replay, changed input/key reuse, competing parents on one revision, stale and ahead revisions, archive filtering and repeated archive, and preserved initial assignments after rename/archive. A Worker clock initially one day behind the actual SQL clock triggers rollback/retry; a clock fixed in 2000 exhausts both attempts with no partial rows. Calendar tests verify the Jakarta midnight boundary and year rollover. These tests do not simulate an independently controllable D1 clock or establish remote clock guarantees.

Browser tests cover direct URLs, refreshes, Back/Forward, unconfirmed-save recovery after Back, hamburger navigation, Home hero and Profile separation, Home/menu separation, add/edit modal focus and cancellation, blocked Escape during an unconfirmed save, create/order/rename/archive, stale comparison with both choices, uncertain response recovery across page restoration, session challenge/rechecking with the same action, read-error recovery, archived/long-name lists, keyboard focus/cancel, and real local D1 persistence across reload. Screenshots of add/edit modals, saved profiles, stale comparison and archived long names were visually inspected in Chromium/WebKit; content wraps and controls remain reachable. Test data is synthetic only.

## Remaining acceptance

Milestone 3 remains open. This work does not implement template editing, later assignment edits, the historical checklist resolver, dashboard point totals, or score/history/correction screens. Archived profiles are retained and manageable; navigation to their historical scores arrives with the child-day/history features. New children have no score contributions, so their initial total is zero; there is no fabricated dashboard balance.

No remote migration or deployment was performed. Before accepting milestone 3, repeat critical atomicity/retry/concurrency cases on isolated staging and establish the SQL-clock freshness/advancement/alignment and before/exactly-at/after-midnight guarantees from [ADR 0001](../adr/0001-scheduled-rule-acceptance.md). A few successful local transactions and Worker clock substitution do not prove those guarantees. Reopen the decision if they cannot be established. Real Access and installed-phone acceptance remain separate checks in the spec.
